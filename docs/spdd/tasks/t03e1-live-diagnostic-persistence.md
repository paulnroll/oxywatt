## Observable behavior

- Existing live W/bpm/rpm, explicit missing reasons, receipt ages and callback counts remain received observations. Zero W/rpm persist as zero; missing stays null/reason. Persist canonical recording/profile/metric observations even outside a recording session, as T03c already supports. Idle standstill can therefore verify real persistence without starting a native ride. No synthetic Recording/Idle, aligned samples or physiological interpretation.
- Show separate **Received callbacks (current run)**, **Committed canonical events (current epoch)**, **Pending events / payload bytes**, **Admission loss (current run)**, **Rejected after stop**, **Storage status**, **Committed revision**, **Last committed receipt time** and local session phase/partial reason. Committed counts include recording/profile/missing events and out-of-session inputs; they are not complete sensor samples or whole database totals. Do not compare lifetime report counts to run-local counters without labels. Keep report saved status separately labelled as timing/status only.
- Count canonical events only after repository commit acknowledgement, deduplicated by batch ID/revision. Standalone effects advance revision but add zero events. An uncertain commit response leaves UI status uncertain until idempotent retry confirms the revision. Read committed receipt/checkpoint from acknowledged repository state, never from latest receipt or in-memory lifecycle. There is no durable transaction wall timestamp in schema v2; do not invent one. After restart, show previous checkpoint as historical and current-run counts as zero.
- Keep constant-size screen state: three received metric slots, fixed counters/status and one bounded error type/reason; publish/refresh at most twice per second. No per-event UI tasks, database reads on Activity/main thread or whole-history rescan after each commit. Recreate/HOME/reopen does not start, stop or duplicate the source or coordinator.
- Canonical readings and the existing validated profile snapshot now enter private app SQLite. The report/log still contains timing/status only. No GPS, sensor IDs, native FIT, unrelated profile fields, exports, network permission or new dependencies. No real-data analysis requests, curves, trends, aggregate membership or older-result fallback. Existing newest-requested/no-fallback contracts remain unchanged.

## Ownership and serialized ordering

1. DiagnosticExtension starts one process-scoped runtime/coordinator before registering the sole source. Database open, cap/provenance validation and recovery initialization run on one background worker; source startup is scheduled only after readiness, without blocking main. Initialization failure visibly disables canonical admission while diagnostic readout may continue. No queue of pre-initialization observations: count them explicitly as not collected, never saved. Activity can obtain an empty read-only model without starting canonical acquisition.
2. Runtime allocates a fresh epoch UUID, monotonic origin and sequence starting at zero for each new source run, including service recreation within the same process. Inject its stamp supplier into the existing adapter; elapsed = current monotonic clock minus origin, UTC is receipt UTC, source measurement time remains absent. Do not use the adapter's process-wide default epoch for this path.
3. Introduce one short shared admission gate around **stamp creation and synchronous handoff**, not merely around accept after a stamp already exists. Adapter keeps its existing delivery serialization; the fixed lock order is adapter delivery lock → admission gate. Under the gate: capture receipt, cut any due timer/flush boundary before the equal-time observation, update fixed received state, call admission.offer, signal the worker. No SQL, JSON encoding, lifecycle application, file I/O, blocking future or SDK connect/disconnect under the gate. Timer/worker never acquire the adapter delivery lock while holding the gate. Source close is requested outside both locks.
4. Only one worker prepares/applies lifecycle and commits. Timer wakeups use one reusable/coalesced signal, not an executor submission per callback. Use one scheduled wakeup for the earliest pending flush/silence/retry deadline, plus the bounded UI cadence. A tick or callback claims an admission batch and its acquisition-time cut under the same gate; the batch remains the existing admission in-flight batch and counts against N01. A single cut watermark is metadata, not an input queue. Later arrivals stay in admission with stamps at/after that cut. While a batch or its subsequent standalone cut effect is outstanding, do not create another handoff or overwrite its cut; release the handoff gate only after both are acknowledged. Callbacks can still offer into the bounded admission queue.
5. Worker applies batch observations once in receipt order (existing lifecycle expires silence before equal-time input), commits that frozen batch, then prepares/commits any envelope-free advanceTime effect through the captured cut **before taking a later batch**. Never advance lifecycle beyond earlier queued inputs. At an exact five-second flush boundary claim the earlier batch before offering the equal-time observation when no batch is outstanding; under stalled storage retain the original cut and explicitly defer subsequent flushes. A timer-only cut is allowed only after earlier admission/loss has drained. Skip unchanged timer effects; do not write checkpoints on every UI tick. Tests must exercise a callback stamped while a worker timer is contending for the gate.
6. A source-terminal latch is separate fixed metadata. onStopped acknowledges adapter quiescence; drain earlier admitted inputs/loss, commit due timer effects, then persist sourceStopped once via prepareEffect. Transport disconnect latches a TRANSPORT_LOSS interruption boundary and disables admission of later callbacks (counted as rejected) before requesting source teardown outside the gate, drain, and end that epoch. Do not silently resume the old session when the SDK reconnects. Initial not-yet-connected status is waiting, not proof of a lost active ride. Repeated lifecycle notifications coalesce; they do not allocate a control queue.
7. A subsequent service-owned source run requires the previous worker's drain/close acknowledgement; until then show stopping/storage blocked and reject duplicate start. Fresh source subscriptions obtain fresh current host state, fresh epoch/admission and conservative lifecycle recovery. FIT binding/cancellation alone is diagnostic metadata, not a save signal or acquisition restart command.

## Retry, loss, shutdown and restart

- On commit failure retain exactly the same PreparedInputWrite ID/content/expected revision and admission batch/cut. No re-prepare, lifecycle replay, early acknowledgement or second write. After success acknowledge that batch under the gate, then commit its cut effects before later handoff. Retry standalone effects identically. Commit success followed by response failure must retry idempotently with no double count.
- During slow/failed writes callbacks may fill the remaining admission budget. Drop incoming telemetry with existing bounded loss metadata; control exhaustion latches stopped and interrupts. Already-stopped offers are a separate bounded rejected counter, since existing offer does not add them to loss metadata. Persist captured loss/terminal when storage permits. Do not silently zero-fill or bridge loss. Frozen JSON/effects are bounded representations of one capped batch, not additional admitted inputs; their allocation overhead remains unmeasured N02 work.
- At main-file cap/FULL retain prior commits, show storage blocked/pending/loss and retry at the fixed cadence; never rotate/delete canonical inputs or keep a parallel measurement file. Existing T02c1 report remains diagnostic only. A full disk may prevent persisting the loss/terminal itself; UI must not claim that it was saved.
- Graceful source teardown runs asynchronously after callback quiescence; Activity close does nothing. Failed drain can remain pending in the process with visible error and no replacement source. Process termination cannot await a guaranteed final commit. No foreground service, fake FIT effects or survival guarantee.
- Abrupt death may lose every uncommitted input, loss accumulator, cut and terminal latch. Restart loads only the committed checkpoint with a new epoch, persists prior-active PROCESS_RESTART interruption before new inputs, and clears current readings. Cold Recording/Paused yields a new partial/ambiguous fragment; Idle is not native save. Never reopen or merge old session UUIDs, replay an uncommitted memory tail, backfill from private FIT, or claim a bounded time loss during stalled storage.
- If effect preparation partially mutates lifecycle then throws, abandon that epoch and stop acquisition; do not replay the batch into that lifecycle. Preserve committed database state and show fatal/unknown tail. Reinitialization uses only its checkpoint and a fresh epoch. No automatic infinite restart loop.
