# T03b — Bounded admission, loss and flush

OWNER-APPROVED 2026-11-11 after merged PR #14. R03/R11, full N01, V17 and flush ordering from V18. T03c–e/T03p remain excluded.

## Contract before implementation

Single serialized owner, no threads or upstream channel. `BoundedAdmission` accepts canonical observations synchronously before lifecycle processing. One FIFO plus at most one in-flight batch share count and payload budgets. Production policy v1: 4096/4 MiB total, 4032/(4 MiB minus 64 KiB) telemetry, 1024 per observation, five-second flush interval. Smaller versioned policies support deterministic stress tests. Payload charge uses a fixed binary-domain encoding budget: 160 fixed bytes plus four-byte length prefixes and UTF-8 bytes for adapter ID/version, normalization version and optional profile version. This conservative representation is independent of future database row size; no SDK objects are retained. Oversize strings are measured without allocating their encoded copies.

`offer` returns admitted, telemetry capacity loss, oversize or stopped. Controls are recording/profile inputs. Invalid epoch/order fails closed. All offered receipts, including dropped ones, must be ordered. Control rejection latches stopped, records loss and retains one terminal interruption outside queue capacity. Restart requires a new admission instance and acquisition epoch, fresh host state and T03a conservative recovery; no reset API exists.

Loss metadata has only first/last receipt, saturating count and a bounded reason set. A batch snapshots loss independently of queue slots. Only one batch may be outstanding; failed writes retain that exact batch and its budget for retry, and later offers accumulate separate loss. Acknowledgement releases capacity only after atomic persistence of observations, lifecycle effects, loss and checkpoint by T03c. Batch identity prevents stale acknowledgement. Lifecycle application is guarded against repetition; if effect computation throws, abandon the epoch and recover conservatively rather than replay partial state. No claim of durable storage is made here.

`applyTo` applies a batch to T03a in receipt order, inserting TRANSPORT_LOSS before each admitted event inside the coalesced loss range and the first event following it (or at the tail), conservatively breaking all continuity. Loss ranges may overapproximate intervening admitted data, never bridge a gap. Terminal CONTROL_OVERFLOW interrupts after retained data. Consumers must persist all returned updates, including envelope-free updates, atomically. Calls occur once per batch; repository retries reuse the computed effects rather than reapply lifecycle. No automatic session merge or zero replacement.

Flush becomes due on capacity pressure, any loss/stop, or five seconds since the oldest pending receipt; this also safely flushes paused/out-of-session data. The owner advances the acquisition clock during silence and polls due before equal-time input. An outstanding batch prevents a second handoff; the deadline remains due until acknowledged. Healthy-storage scheduling and actual writer integration remain T03e responsibilities.
