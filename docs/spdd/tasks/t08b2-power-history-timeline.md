## Problem, goal and scope

R08 requires seeing how recorded training observations evolve over time in the Karoo plugin. T08b1 displays one explicitly bound session and cannot answer that question. First useful increment: a chronological scatter plot of saved observed best mean power at one selected duration, in the existing app and a separate graphical **OxyWatt · Power history** ride field. Existing **Saved power curve** registration and binding remain compatible.

This is a raw historical observation view, not a physiological estimator or smoothed trend. R04/R07/R08/R09/R10/R11/R12 apply. Dependencies: merged T04b4 result authority, T08b1 projection/rendering approach, existing SessionSnapshot.trendEligible and the source-owned canonical-first worker. Full automatic post-workout calculation, native save identity, full historical paging and background lifecycle acceptance are separate work. A saved training session without an existing supported result must appear with a reason; viewing history never silently calculates it.

## E / A / S — Entities, approach and structure

One runtime-only immutable HistorySnapshot retains at most 20 inspected session entries, each with UUID, receipt UTC, status, eligible point if any, current generation and provenance identity. Versioned history presentation policy `power-history-v1` governs eligibility/order/rendering. Small versioned preference stores duration/appearance only. No persisted derived values, aggregate membership writes, copied curves or new schema/store/core engine. Reuse existing result validation; factor only a minimal shared validator if necessary, with unchanged single-session behavior tests.

One HistoryController on the existing worker coalesces refresh/configuration commands. Begin after canonical work; enumerate once, resolve at most one session/newest-result entry per worker opportunity, yield to canonical ingestion between entries. At most 20 entries per refresh, with one cancellable refresh in progress and one coalesced replacement request. No raw observation replay or per-callback history scan. Each session/result read must validate exact identity/current generation before publication; sequentially gathered history is an explicitly bounded refresh snapshot, not a global atomic database snapshot. Invalidate/restart or suppress affected entries if newest authority changes; never claim atomicity from separate reads. On successful terminal result invalidation, suppress affected numeric output until reload. While either app history or field is visible, schedule at most one refresh start per five seconds; hidden views do not poll. Final pre-publication authority checks also yield to canonical work and remain bounded. A read failure publishes an error, not a partial successful chart. If actual repository APIs cannot ensure this, stop and revise the proposed read boundary before implementation.

Reuse existing source-owned runtime, SDK 1.1.9 DataTypeImpl/RemoteViews approach and per-view <=512×512 bitmap / <=1 Hz changed-output limits. Subscription cancellation releases work; attaching/hiding history does not start collection, analysis, another worker or a database owner. Worker absent: **Open OxyWatt · History unavailable**. No SDK pin, permission, storage-cap, retention or collection-policy change. No new framework. Expected ownership: new history model/controller/preferences/presentation/renderer/type and focused tests, minimal runtime/Activity/resource/extension-registration hooks, and coordinated documentation. Existing persistence API changes, if needed, must be read-only and explicitly reviewed; no new full-table/raw-input scan.
